# Runbook: SES production access for verification-code email

This is an **operations runbook, not code**. It is the whole of issue #6. Amazon
SES starts every account in *sandbox mode*, which delivers only to addresses you
have pre-verified — fine for the team, useless for a real user registering with
her own address. Leaving the sandbox is a support request with about a day of
lead time, and AWS refuses vague ones. This ticket exists so that day is spent
now rather than the week the [Accounts context](../../services/backend/CONTEXT.md)
needs to send its first real verification code.

Nothing in the codebase blocks on this, which is exactly why it gets forgotten.
Work the checklist top to bottom; each heading is one acceptance criterion.

> **Who does what.** Every step here needs a registrar account, DNS access, or the
> AWS console — human actions with credentials and, for the domain, money. An
> agent cannot perform any of them. What the agent produced is the request draft
> in [§5](#5-submit-the-production-access-request) and the exact records in
> [§2](#2-publish-spf-dkim-and-dmarc); a person executes the rest.

## Decide two things first

**Region.** Production access is granted **per AWS region**. Pick one region and
do everything below in it — verifying the domain in `eu-west-1` does nothing for
`us-east-1`. Recommended: **`eu-west-1` (Ireland)** — EU data residency, close to
users in Egypt, full SES feature support. If the team already runs infra in
another region, match it. Record the choice in `infra/envs/*.env` when the
sending code lands.

**Sending identity.** See [§6](#6-agree-a-sending-identity). Agree it before you
write the request in §5, because the request names it.

---

## 1. A domain the team controls, with manageable DNS

- [ ] Register a domain, or carve out a subdomain of one the team already owns.
- [ ] Confirm you can add TXT, CNAME and MX records to its DNS zone.

You cannot send from a domain you cannot prove you control, and DKIM/DMARC below
are DNS records — so a domain with no manageable DNS is a dead end. If the team
has an existing domain, a subdomain dedicated to mail (e.g. `mail.example.org`,
sending as `verify.example.org`) keeps this project's DNS changes isolated from
whatever else that domain does.

Any registrar with DNS hosting works (Route 53, Cloudflare, Namecheap, …). If you
use **Route 53** in the same AWS account, SES can write the DKIM records for you
in step 3 — the one place the console removes manual work.

---

## 2. Publish SPF, DKIM and DMARC

Three mechanisms, three record types. Publish all three: a mailbox provider that
sees SES-signed mail with none of them is within its rights to bin it, and this
mail is a one-time code the user is actively waiting for.

Replace `example.org` with the real domain throughout. The `<...>` values are
generated by SES in step 3 — publish DKIM **after** you have them.

### DKIM — proves the message was not altered and comes from you

SES **Easy DKIM** generates three CNAME records. Publish all three exactly as
shown in the console:

```
<token1>._domainkey.example.org.  CNAME  <token1>.dkim.amazonses.com.
<token2>._domainkey.example.org.  CNAME  <token2>.dkim.amazonses.com.
<token3>._domainkey.example.org.  CNAME  <token3>.dkim.amazonses.com.
```

### SPF — authorises SES to send for your MAIL FROM domain

Set a **custom MAIL FROM subdomain** in SES (e.g. `bounce.example.org`) so that
SPF *aligns* with your domain for DMARC. SES then asks you to publish, on that
subdomain:

```
bounce.example.org.  MX   10 feedback-smtp.eu-west-1.amazonses.com.
bounce.example.org.  TXT  "v=spf1 include:amazonses.com ~all"
```

Use the `feedback-smtp` host for **your chosen region** — the console prints the
exact one. Without a custom MAIL FROM, SES uses `amazonses.com` as the MAIL FROM,
SPF passes but does **not** align to `example.org`, and DMARC then leans entirely
on DKIM. Aligning both is the belt-and-braces choice, and this is code-delivery
mail — take it.

### DMARC — tells receivers what to do when a check fails, and reports back

One TXT record. Start permissive, then tighten once the reports are clean:

```
_dmarc.example.org.  TXT  "v=DMARC1; p=none; rua=mailto:dmarc-reports@example.org; fo=1"
```

- [ ] Publish the three DKIM CNAMEs (after step 3 generates them).
- [ ] Publish the MAIL FROM MX + SPF TXT.
- [ ] Publish the DMARC TXT with `p=none`.
- [ ] Point `rua=` at a mailbox someone will actually read for a week or two.

**Move to enforcement once reports show only your own aligned mail passing:**
`p=none` → `p=quarantine` → `p=reject`. Do not ship `p=reject` on day one; a
single misconfigured record then silently drops every verification code.

## 3. Verify the domain in SES

In the **SES console → Identities → Create identity → Domain**, for your chosen
region:

1. Enter `example.org`.
2. Enable **Easy DKIM** (RSA 2048-bit). SES shows the three CNAMEs from §2.
3. Set the **custom MAIL FROM** subdomain (`bounce.example.org`); SES shows the
   MX + SPF from §2.
4. If DNS is in Route 53 on the same account, let SES **publish the records for
   you**. Otherwise copy them into your DNS host by hand.
5. Wait for propagation. Identity status goes **Verified** and DKIM goes
   **Successful** — usually minutes, allow up to 72 hours.

- [ ] Identity status: **Verified**.
- [ ] DKIM status: **Successful**.
- [ ] Custom MAIL FROM status: **Successful**.

Verify the **domain**, not a single address — an address identity cannot back
arbitrary `From:` users and does not survive rotating the sending address.

---

## 4. (still sandbox) Prove the flow works before asking

While still in sandbox you can only send to verified recipients — so verify one
team address and send yourself a test, to prove the identity actually delivers
before you spend the request on it.

- [ ] Verify one team email address as a recipient identity.
- [ ] Send a test from the domain to it; confirm it arrives and passes SPF/DKIM/
      DMARC (check the receiving provider's "show original" / auth-results).

If the test fails auth here, the production request will be slower — fix DNS
first.

## 5. Submit the production-access request

**SES console → Account dashboard → Request production access.** (Older accounts
route this through a Service Quotas / support case; the fields are the same.)
Choose **Transactional** as the mail type.

AWS refuses vague requests. Paste the draft below, edited for the real numbers,
into the use-case description. It says the four things a reviewer looks for:
*what* the mail is, that recipients *asked* for it, that you *handle bounces and
complaints*, and that the *volume is small and self-limiting*.

> **Use case.** HerHealthGPT is a reproductive-health triage web application. SES
> is used for one purpose only: sending **transactional one-time verification
> codes** to confirm a user controls the email address on her own account, plus
> the matching password-reset code. This is not marketing mail — there are no
> newsletters, campaigns, or bulk sends, and there is no mailing list.
>
> **Recipients** are only people who have just entered their own address into our
> registration or password-reset form; every message is triggered by that user's
> own action seconds earlier. We do not send to purchased, scraped, or imported
> lists.
>
> **Volume** is low and self-limiting: on the order of a few hundred emails per
> day at launch, one code per registration or explicit resend. Resends are rate
> limited per address, and a code becomes unusable after a handful of wrong
> attempts, so the address cannot be used to relay unwanted mail.
>
> **Bounces and complaints** are handled: we consume SES bounce and complaint
> notifications via SNS, stop sending to any address that hard-bounces or
> complains, and monitor the account reputation dashboard. Sending domain has
> Easy DKIM, an SPF-aligned custom MAIL FROM, and an enforced DMARC policy.
>
> **Sending identity:** `no-reply@example.org` (display name "HerHealthGPT"),
> from region `eu-west-1`.

- [ ] Expected daily volume (a real estimate, not "a few hundred" if you know

## 6. Agree a sending identity

Decide, and write down, the address verification codes come **from**. Once
production access is granted it is tied to the verified domain, so changing the
*domain* later means re-verifying; changing the local part (`no-reply` →
`codes`) is free.

Recommended:

- **From:** `no-reply@example.org`, display name **HerHealthGPT**.
- **Reply-To:** a monitored support address (`support@example.org`) — a code
  email that bounces silently when a confused user replies is a bad first
  experience for a health service.
- Keep it consistent with the Accounts language: this address sends a
  **Verification** code, never an "activation" or "confirmation" link.

- [ ] Reply-To agreed: `__________`.

Production access is granted or refused; either way it is written down so the

Refusal is a valid outcome of this ticket — a recorded reason and a chosen
fallback closes it just as well as a grant does.
